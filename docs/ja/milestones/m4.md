# M4：多態化・ランチャー・プラットフォーム・Steam

M4 は、ビルドごとの差異化、クロスプラットフォームでの起動、Steam を対象とします。本プロジェクト自身のオープンコアの分割に従い、**多態化エンジンとネイティブランチャーはクローズドのコンポーネント**であり、Steam と Proton は、それぞれの検証に専用のハードウェアを必要とします。このページでは、オープンなベースラインがここで何を実装し検証したのか、そして何がクローズドまたはハードウェア待ちなのかを正確に示します。

## ビルドごとの差異化（ベースライン、動作済み）

「1 つのゲームの解析結果を次のゲームに流用できない」という性質は、ベースラインの段階から始まっています。`protect` を実行するたびに、暗号学的に独立したビルドが生成されます。

- ランダムな 16 バイトの `container_id` がすべての鍵導出（HKDF）のソルトとなり、これに加えてファイルごとのランダムな ID と鍵、チャンクごとのノンスが使用される
- その結果、同じゲームを 2 回保護すると、異なる `container_id`、異なるファイルごとの鍵、異なるコンテナが得られ、あるビルドの鍵で別のビルドを読むことはできない。これは `tests/test_cli.py::test_two_builds_are_cryptographically_independent` で実証されている
- スクリプト鍵はコンテナ鍵から独立している（[スクリプト層](../technical/script-layer.md)を参照）

ベースラインがランダム化**しない**もの：コンテナのバイトレイアウトとフィールドの順序、およびスクリプトの AST のクラス名で、これらは標準のまま（再暗号化のみ）です。

### クローズドでの強化：多態化エンジン

クローズドのバイナリプラグインは、ビルドごとに*構造*、すなわちコンテナのレイアウトとコンパイル済みスクリプトのエンコードをランダム化するため、鍵を手にしていても汎用的な読み取りツールやデコンパイラを書くことはできません。このプラグインは、安定した、文書化されたプロセスインターフェースを介して `renmori protect` に組み込まれます（[アーキテクチャ](../technical/architecture.md)と[オープン部分とクローズド部分のインターフェース](../technical/plugin-interface.md)を参照）。オープンな CLI が統合の起点です。利用可能なプラグインがない場合、デフォルトのフル保護はベースラインに格下げせずに失敗し、ベースラインへフォールバックするのは `--strength auto` を指定した場合のみです。その仕組みと実装は独自のものであり、非公開リポジトリ `MewBaka/RenMori-core` で管理されています。

## ランチャーとプラットフォーム

ベースラインは Ren'Py の**拡張機構**（`game/renmori.rpe`）を通じて読み込まれ、通常の起動処理の中で Ren'Py に同梱された Python の内部で動作します。この仕組みはプラットフォームに依存しません。同じ `.rpe` が Windows、macOS、Linux、Steam Deck で動作するのは、OS ごとのランチャーのバイナリではなく、Ren'Py の Python と `ctypes` のみに依存しているためです。

プラットフォームごとの AES-GCM バックエンド（単一のインターフェース、`container/crypto.py`）は次のとおりです。

| プラットフォーム | バックエンド | 状況 |
|----------|---------|--------|
| macOS（arm64/x86_64） | `librenpython.dylib` がエクスポートする OpenSSL EVP | **ここで検証済み**（往復テストとエンジン内でのテスト、Ren'Py 8.5.2） |
| Linux / Steam Deck | `librenpython.so` がエクスポートする OpenSSL EVP | エンジン内で**検証済み**（CI、ヘッドレス）、macOS と同じコード経路、Steam Deck での実行は未検証 |
| Windows | OS の CNG（`bcrypt.dll`）、ハードウェア AES | Windows のエンジン内で**検証済み** |

ライブラリは Python の実行ファイルと同じ場所から探され（`runtime_lib_candidates`、単体テスト済み）、`CDLL(None)` を介して読み込むことはありません。

### ネイティブランチャー（クローズド、オプション）

クローズドのプラグインには、`--launcher` で有効にするプラットフォームごとのネイティブランチャーが含まれます：

- **起動時の認証**：ビルドごとの起動シェアを保持し、ランタイムはこれを**実行時の鍵導出**に組み込むため、ランチャー経由で起動したときにのみ鍵が復元され、同梱のネイティブコアをオフラインで呼び出しても誤った鍵しか導出できない
- **起動時の完全性検査**：エンジンを起動する前に、余分な `.rpe` や単体のスクリプトなど、Ren'Py がコンテナの外から実行するファイルが配布物にあれば起動を拒否する。1.2.5 以降は `game/renmori.rpe` と `renpy/common` 内のスクリプトも鍵に組み込む
- **組み込み方法**：macOS では `.app` に自動で組み込まれる（ビルド時に自動で ad-hoc 署名され、無料で、Apple Silicon では必須であり、Developer ID での再署名も可能）。Windows と Linux では独立したファイルとして同梱され、手動で組み込む必要がある
- **検証状況**：3 つのプラットフォームでビルドと単体テストを実施し、macOS ではエンジン内で検証済み

**ベースラインは新たな実行ファイルを配布しない**ため、元の Ren'Py のビルドと比べて署名の負担が増えることはありません。

## Steam

- **デフォルトのビルドでは Steam オーバーレイは構造上安全**：オーバーレイはゲームのプロセスに DLL を注入するが、RenMori（`--launcher` なし）は Ren'Py の*ファイル読み込み*をフックするだけで、プロセスへの注入や DLL インジェクションも、ホットパスでの改ざん対策も一切行わないため、オーバーレイを阻害することはあり得ない。`--launcher` を使う場合、オーバーレイと Steamworks SDK は macOS でのみ検証済みで、Windows と Linux は未テスト
- **`renpy.loader` の外で読み込まれるファイルはディスク上に残る**：Steam SDK は `steam_appid.txt` を（ローダーを経由せず）直接読み込むため、このファイルはデフォルトで暗号化されない（`DEFAULT_KEEP_ON_DISK`）。同様のファイルは `renmori.toml` の `keep_on_disk` で追加できる。これは `tests/test_cli.py::test_steam_appid_kept_on_disk` で実証されている
- **実績と Steam クラウドのセーブデータ**は Ren'Py の Python API を経由し、この API には手を加えない。`.rmc` は静的なファイルであるため、Steam のファイル検証とアップデートも通常どおり機能する
- **Steam DRM による二重のラップを行わない**：Steam DRM は実行ファイルを書き換えるため、ネイティブランチャーの自己検査と衝突するおそれがあり、いずれにせよ保護としては弱い

Steam、Proton、Steam Deck での完全な実行は、対応するハードウェアの用意を待っている段階です。上記の性質は構造に基づくもの（フックとファイルの配置による）であり、ここでは実行テストを行っていません。

開発者向けのリリースの流れ（ビルド、保護、SteamPipe でのアップロード、どのファイルをどのデポに入れるか、起動オプション）については、[Steam へのリリース](../integration/steam-release.md)を参照してください。

## M4 のその他の内容

- `renpy.exists()`（以前はディスクのみが対象）がコンテナも参照するようになったため、これを使ってファイルの有無を確認するゲームからも格納済みのファイルが見えるようになった（`_install_exists_fallback`）

## 現在の状況

macOS 上の Ren'Py 8.5.2 で検証済みのオープンなベースラインは、ビルドごとの差異化、クロスプラットフォームの `.rpe` の経路、Steam 向けのファイル配置と構造上のオーバーレイの安全性、`renpy.exists` のフォールバックです。ランタイムは Windows と Linux のエンジン内でも検証済みです。クローズドでプラグインとして提供済みのものは、多態化エンジンと鍵を導出するネイティブランチャーです（macOS ではエンジン内で検証済み、Windows と Linux ではビルドと単体テストを実施）。ハードウェア待ちのものは、Steam と Steam Deck での実機による実行です。
